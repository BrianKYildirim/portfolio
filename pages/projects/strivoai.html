01 Overview

Five career workflows on one analysis pipeline

StrivoAI is an AI career platform: resume analysis, LinkedIn grading, Career Compass, Recruiting Lens and interview prep. Each tool asks a different question, but they all run on the same pipeline: the browser submits work, a Supabase Edge Function records it as a job, model calls run in parallel, and the client polls for the result.

It is built for students and early-career engineers who want concrete, role-specific feedback on their materials instead of generic advice.

02 How it works

Long analyses run as jobs, not as one long request

A job that survives a closed tab

A submit-*-analysis-job function validates the request, inserts a pending row into analysis_jobs, starts the matching process-*-analysis-job worker and answers with the job id and a poll interval. If the same work is already pending, retrying or processing, it returns that job instead of starting a second one, so a double click or a reload doesn't start duplicate work.

Parallel calls instead of one oversized request

Each feature splits its analysis into independent model calls that run concurrently, and each call returns structured output (a fixed JSON shape) rather than free text. Wall-clock time is set by the slowest call rather than by the sum of all of them.

Domain-aware, tier-aware, OCR when needed

  • Analyses are framed by the user's current goal, such as Software Engineering · Internship, rather than by generic resume rules.
  • Stripe subscription tiers are enforced twice: the frontend hides what a plan can't use, and the Edge Functions check the tier again on the server.
  • When a PDF has no usable text layer, an ocr-pdf function extracts the text so scanned resumes still work.

03 Engineering challenge

Cutting the time an analysis takes

The problem
A full analysis took too long to hold one HTTP request open, and too long to watch a spinner.
Decision
Run every analysis as a job recorded in Postgres, split it into independent model calls that run in parallel, and let the client poll for the result.
Why
Parallel calls bound the latency by the slowest call instead of the sum; the job row outlives a dropped connection or a closed tab; and polling works through any proxy or network.

05 Lessons learned

Latency is an architecture decision

Latency was set by the shape of the work: independent calls running in parallel finish when the slowest one does, and a job the client can come back to removes the need to keep one connection alive.

Checking plans on the server as well as in the UI means the interface is never the only thing standing between a free account and a paid feature.

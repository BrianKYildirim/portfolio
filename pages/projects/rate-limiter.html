01 Overview

A per-key token bucket built for contention

An in-process rate limiter for C++20. Every key, such as a user id or an IP address, gets its own token bucket with a capacity and a refill rate. allow(key, limit) takes one token if there is one and returns whether the call is allowed, how many whole tokens remain, and how many milliseconds until the next token if it isn't.

It is thread-safe with linearizable per-key decisions, ships a C API and an optional JNI bridge for Java, and is covered by GoogleTest unit, concurrency and differential tests plus Google Benchmark suites.

Every decision and bucket reading here comes from ratelimit-cpp itself at commit b577e6f, compiled to single-threaded WebAssembly and called through its C API (rl_allow_at, rl_inspect_at). The traffic is synthetic and the clock is virtual; nothing here measures speed.

What runs here
  • Source: the ratelimit-cpp tree at this commit and the build manifest.
  • Built by the library's scripts/build-wasm.sh with Emscripten 7.0.0, and rebuilt from the pinned commit to identical bytes. The manifest records the toolchain, the flags and the hash of each file.
  • A parity test replays shared request traces through native builds (GCC and MSVC) and through this WebAssembly build, and requires identical decisions and inspection values. All three builds matched, and this site's automated tests replay the same traces through the shipped module against the recorded native output.
  • Differences from native:
    • One thread, so there is no lock contention to observe.
    • The demo passes its own virtual time to rl_allow_at and rl_inspect_at. The library's header says that time should come from rl_now_ns.
    • FastClock and the TSC are not used. The one clock reading left, a steady_clock reading that seeds the hash table, only places keys in slots and never changes a decision.
    • rl_evict_idle is not exported, so it is never called.
    • A C++ exception stops the WebAssembly module (the build keeps Emscripten's default exception handling), and the demo then offers Retry, which loads a fresh module. Natively, of the functions the demo calls, only rl_new_inproc (which returns NULL) and rl_free catch exceptions; rl_allow_at and rl_inspect_at have no catch blocks.
    • The toolchain is Emscripten rather than GCC or MSVC.

03 How it works

One hash, one cache line, one short lock per decision

Exact refill without floating point

Balances are stored in nanotokens (109 per token). Refilling for dt nanoseconds at rate tokens per second then adds exactly dt × rate nanotokens: one 64-bit multiply with an overflow check, no division and no rounding drift between calls. Long idle periods and huge rates saturate at capacity instead of wrapping.

Lookups without a shared lock

Each shard publishes its hash table as a single word, so a lookup reads the table without taking any lock and can prefetch the key's slot before the clock is read. Inserts take the shard's mutex, and a new key usually fills an empty slot in place; growth and eviction build a new table, and the old one is freed by epoch-based reclamation only once no reader can still be inside it.

Denying without writing

A denial less than 1 ms after the key's recorded time changes nothing, so a thread that recently saw a key denied decides from a seqlock snapshot without taking the slot's lock. A flood of requests for one over-limit key then leaves its cache line shared by every core instead of bouncing between them. Refill is linear and exact, so skipping those writes changes no later verdict.

04 Engineering challenge

A hot over-limit key made every core write the same cache line

The problem
When many threads hit one key that is over its limit, every denial still wrote the key's balance and timestamp. Each write pulls the cache line into one core exclusively, so the line bounced between cores and a flood of requests for one key could not scale across them.
Options considered
  • std::mutex per shard. Simple and correct, but every decision for a hot key serializes on one mutex, and every denial still writes.
  • Write-intent prefetch. Fetch the slot ready for writing before locking. Measured: it was slower on a hot key, because it takes the line away from every other core.
  • Per-slot spinlock + read-only denials. A version lock inside each 64-byte slot, held for a few dozen instructions, and quiet denials decided from a snapshot. ✓ chosen
Decision
Lock only the key's own slot, spin briefly with exponential backoff before yielding, and deny over-limit keys without writing when nothing would change.
Why
The critical section is a few dozen instructions, so a waiting thread spins with exponentially longer pauses instead of going to sleep, which also keeps it from pulling the cache line away from the holder, and yields only in case the holder was preempted. Because the lock lives in the key's own slot, decisions for different keys never take the same lock, and a key a thread has just seen denied can be denied again from a snapshot without taking it.

05 Results

What the benchmarks measure

  • 153.3Mcalls per second on one hot key that is over its limit, so almost every call is denied, at 8 threads on Ubuntu on WSL2; range 116.7–178.2Mmedian of 10 runs
  • 3.5×as many denied calls per second at 8 threads as at 1, on the same hot key, on Ubuntu on WSL2; range 2.5–3.9×median of 10 runs
  • 134.2heap bytes per key with 1,000,000 short keys, counted by a heap-accounting allocator on Ubuntu on WSL2; range 134.2–134.2median of 10 runs
  • 50.9Mcalls per second on the same hot-key workload on Windows 11, native, same laptop; range 35.4–67.7M. Against the first figure: faster on Ubuntu on WSL2 by ~3.0×, medians of 10 runs eachmedian of 10 runs

The library has two benchmark programs: rl_bench, built on Google Benchmark, and rl_latency. Together they measure:

  • throughput as wall_ops/s (all threads' calls divided by wall time) across thread counts, for one hot key, many shared keys and per-thread keys;
  • the amortized time per call on a single thread (wall time divided by calls), and the cost of inserting new keys;
  • latency percentiles, from rl_latency;
  • the overhead of read-only inspection with inspect();
  • memory per tracked key.

Each figure above is the median of 10 interleaved runs on one laptop, under Ubuntu on WSL2 (GCC 15.2, -O3) and under native Windows 11 (MSVC 19.43, /O2), with the lowest and highest run as its range. Why the hot-key workload is slower on Windows is a hypothesis, not verified: MSVC and GCC generate different code, and under MSVC FastClock falls back to steady_clock.

The README section Performance: what I measured and how describes how each benchmark is run, the method and both machines, with full tables for both environments (as of eef537d). The playground above runs the library itself, compiled to WebAssembly, on a virtual clock with synthetic traffic; it shows no timings and measures nothing about native or multithreaded speed.

06 Lessons learned

Measure the cache line, not the instruction count

An optimization that looks free can be a loss: a write-intent prefetch seems ideal for a slot that is about to be written, and it measured slower on a hot key.

An earlier Q32.32 fixed-point balance overflowed for capacities above 232; integer nanotokens with explicit overflow checks removed that whole class of bug, and a test pins it.

A differential test against an independent model (a std::map, with exact division in place of the engine's overflow checks) checks the optimized engine over random operations, including clocks that go backwards.

07 What's next

From one process to many

  • The limiter is in-process: buckets aren't shared across processes or machines. A distributed tier in front of a shared store would be the next step for multi-instance services.
  • Eviction is manual today (evict_idle()); a background sweeper would bound memory automatically.

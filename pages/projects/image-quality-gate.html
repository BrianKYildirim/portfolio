01 Overview

One endpoint that says whether an upload is usable

Image Quality Gate is a REST microservice that scores an uploaded image for sharpness and brightness and returns a single is_ok. An upload pipeline can call it before storing a photo and ask the user to retake a blurry or badly lit one, instead of discovering the problem later.

An image passes when blur_score ≥ BLUR_MIN and BRIGHT_MIN ≤ brightness ≤ BRIGHT_MAX. The response also carries both scores, the processed size and the thresholds that were applied.

A JavaScript port of the service's analysis at commit 436fe53 runs in this tab: EXIF orientation, a Pillow-compatible Lanczos resize to 1600px, OpenCV grayscale, variance of Laplacian and mean brightness. It was compared with the Python service while it was written, but it is a port, and results can differ (see Known differences). Nothing is uploaded.

What's ported
  • Ported: app/services/preprocess.py (load_and_normalize, to_gray), app/services/quality.py (variance_of_laplacian, brightness, assess), the defaults in app/core/config.py and the Docker image's values from .env.example, which a container built from the Dockerfile copies to .env. The Lanczos resize reproduces Pillow's fixed-point resampler byte for byte; grayscale uses OpenCV 5's coefficients.
  • Decoding and EXIF orientation are done by your browser (createImageBitmap) instead of Pillow; colour profiles are ignored on both sides. Errors mirror the API's 415, 413 and 400 answers.
  • Known differences: transparent images (browsers drop the colour under fully transparent pixels, Pillow keeps it); formats only one side can decode; browsers that add privacy noise to canvas reads; and OpenCV 4.x, whose grayscale rounding differs by one level on some pixels.
  • The 32-megapixel limit is this demo's own browser guard. The service rejects images over 25 megapixels (MAX_IMAGE_PIXELS) with 400 Invalid image data, checking the header before decoding, so an image between the two limits is scored here but would be rejected by the service.

03 How it works

Five steps from upload to is_ok

Why the variance of the Laplacian measures focus

The Laplacian is a second derivative: it is near zero where brightness changes smoothly and large where it changes abruptly, at edges. A sharp image has many strong edges, so its Laplacian values spread widely and their variance is high. Blur softens edges, the values cluster near zero, and the variance drops.

A small service, run like a real one

  • FastAPI with Pydantic settings: every threshold and limit is an environment variable with a validated default.
  • Middleware echoes an incoming X-Request-ID or generates one, so a request can be traced through JSON logs.
  • The Prometheus instrumentator exposes request metrics at /metrics.
  • The Docker image runs two uvicorn workers; CI runs ruff, black, mypy and pytest on every push.

04 Engineering challenge

Picking a blur threshold from data instead of by eye

The problem
The blur score depends on image content and resolution as much as on focus, so no single BLUR_MIN is right for every source of images.
Options considered
  • A fixed, hand-picked value. Quick, but tuned to whatever images happened to be on hand.
  • A labelled sharp/blurry set. Accurate, but someone has to label it for every new source.
  • Otsu's method over a folder's scores. Unsupervised and repeatable. ✓ chosen
Decision
scripts/tune_blur.py scores a folder of representative images with a copy of the service's preprocessing and scoring and suggests BLUR_MIN with Otsu's method over the log10 of the blur scores, plus brightness bounds from the central 95% of brightness values.
Why
Otsu's method picks the split that maximizes the variance between the two groups, which separates a "sharp" cluster from a "blurry" one without labels; the log scale matches how blur scores spread over orders of magnitude.

06 Lessons learned

A score is only as good as what it can't see

The blur score is content-dependent: a sharp photo of a smooth, textureless surface scores low, and darkening an image lowers its score too, because it shrinks every edge. The Underexposed sample in the demo shows both checks failing at once.

Pin computer-vision dependencies: OpenCV's grayscale rounding changed between 4.x and 5.x, enough to move scores slightly, and requirements.txt doesn't pin opencv-python-headless.

07 What's next

Beyond blur and brightness

The decision is based only on blur and brightness, so an image can pass while showing the wrong subject or unreadable text. Adding checks like those is the natural next step for a real upload pipeline.

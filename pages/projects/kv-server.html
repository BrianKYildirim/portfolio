01 Overview

A text protocol over raw TCP, one thread per client

A key-value server written with nothing but Python's standard library. server.py listens on port 3490, starts one thread per connection, at most --max-connections at once (100 by default, limited by a threading.BoundedSemaphore), and answers five text commands: SET key value, GET key, REMOVE key, PRINT and quit. Every change is persisted to store.txt, one key⇥value line per entry, and loaded again on start. On Ctrl+C it stops accepting, lets running commands finish, and closes each open connection before exiting.

client.py is the matching interactive client: it sends one line, waits for one response, and prints it.

Real protocol · simulated network

The command parser and store are line-for-line ports of server.py, so responses and store.txt match the real server byte for byte. Sockets, threads and the lock are simulated so you can watch them; no network connection is made, and timings are slowed down for visibility.

What's ported
  • Ported from server.py: KeyValueStore (load, save, set, get, remove, print_store), CommandParser, the flow of handle_client and its print() lines. From client.py: one send, one recv(1024), and its output lines. Verified against the Python classes with 22 command vectors.
  • Simulated, not real: TCP, accept(), the threads, threading.RLock and the file on disk. The socket byte streams are modelled, so a response longer than 1024 bytes is split across reads the way client.py would see it.
  • CPython's lock is not FIFO-fair; the queue is shown in arrival order for clarity. The RLock's count never exceeds 1, because save() doesn't acquire the lock.
  • Python's split(), strip() and upper() match JavaScript for ASCII; they differ only on rare Unicode whitespace and case mappings.
  • client.py sends nothing for an empty line and then waits forever, so Send needs at least one character. A real client notices a restarted server on its next read; the demo shows it immediately.
  • Durations are fixed constants, slowed for visibility, not measured.

03 How it works

Every request takes the same path through one lock

Thread per connection, under the GIL

CPython's global interpreter lock lets one thread run Python code at a time, but a thread blocked in recv(), sendall() or a file write releases it. A server that mostly waits on sockets therefore still serves clients concurrently. The cost is one operating-system thread per open connection; a bounded semaphore caps how many exist at once, and further clients wait in the listen backlog until a slot frees up.

Persistence by full rewrite

Every SET, and every REMOVE that finds its key, reopens store.txt for writing and writes the whole dictionary. The file always matches memory after a successful write, but each write costs time proportional to the whole store, and a crash in the middle of one can leave the file truncated.

A protocol without framing

A command is whatever one recv(1024) returns. TCP is a byte stream, so two quick sends can arrive in one read and a long one can be split. client.py also reads exactly one recv(1024) per response, so a PRINT longer than 1024 bytes leaves the rest in the socket, and the next command shows the leftover instead of its own answer. The playground reproduces this.

04 Engineering challenge

Keeping the dictionary and the file consistent across threads

The problem
Two clients writing at once could interleave a dictionary update with another thread's file rewrite, leaving store.txt out of step with memory.
Options considered
  • No lock. Works until two writes overlap.
  • A lock per key. More concurrency, but every write rewrites the whole file anyway.
  • One lock around every store operation, including the file write. ✓ chosen
Decision
A single threading.RLock guards every KeyValueStore method, and the file rewrite happens while it is held.
Why
Simple and correct at this scale: each write updates memory and disk as one step, and readers never see a half-applied change. Honestly, the RLock is never re-entered, because save() doesn't take the lock, so a plain Lock would do the same job. And holding the lock during disk I/O makes every client wait for each write.

06 Lessons learned

A byte stream is not a message stream

TCP delivers bytes, not commands. Without a delimiter or a length prefix, the server only works because each client waits for an answer before sending again.

A lock makes a design correct; it doesn't make it fast. Here every client queues behind the same file write.

07 What's next

What a second version would change

  • Newline framing on both sides, so commands and responses can't merge or split.
  • An append-only log with periodic compaction instead of rewriting the whole file on every change.
  • A thread pool, or selectors / asyncio, instead of one thread per connection.
  • Quoted values, so a value can contain spaces.

01 Overview

The cheapest anvil order for any set of enchantments

In Minecraft, every anvil merge costs experience levels, and every merge also raises the item's prior-work penalty, which is added to all later merges. Combine the same books in the wrong order and the total cost climbs, or a single step passes 39 levels and the anvil refuses with "Too Expensive!".

The calculator takes an item and the enchantments you want, builds the missing books, and returns the cheapest sequence of merges, optimized either for the fewest levels or for the least prior work on the finished item.

02 How it works

Split, solve both halves, merge, and remember every answer

Why memoization is what keeps it fast

Splitting every subset into two non-empty groups, all the way down, visits roughly 3n combinations: each item is either in the left half, the right half, or outside the current subproblem. Items are frozen dataclasses with a stable hash, so a tuple of them is a valid lru_cache key and each subset of books is solved exactly once.

The anvil rules, as code

  • A merge costs both items' prior-work penalties (2uses − 1 levels each) plus the sacrificed item's enchantment value (level × weight).
  • An item can't be sacrificed into a book (InvalidTarget), and any merge above 39 levels raises MergeTooExpensive; both are skipped, which also prunes the search.
  • The merged item's anvil uses are one more than the larger of the two inputs.

03 Engineering challenge

Optimizing two objectives without losing either

The problem
The plan with the fewest levels can leave the item with more prior work, which makes every later repair or enchantment more expensive. Some players want one, some the other, so keeping a single "best" plan per subproblem would throw away answers.
Options considered
  • One combined score. A single number to minimize, but the weighting decides the answer for the player.
  • Two independent searches. Clear, but doubles the work.
  • One best plan per prior-work value. A small frontier carried through the same search. ✓ chosen
Decision
Every subproblem returns a dictionary keyed by the result's anvil-use count, holding the cheapest plan in levels for each. At the end the mode picks: fewest levels (ties broken by prior work) or least prior work (ties broken by levels).
Why
The prior-work count is bounded by the number of merges, so the frontier stays tiny. And each enchantment appears in exactly one book, so every order of the same books ends with the same enchantments: two plans that also share a prior-work count produce identical items, and only the cheaper one can ever matter.

05 Lessons learned

The data structure decided the algorithm

Making items immutable and hashable was what made memoization a one-line decorator instead of a hand-written cache.

Keeping a small set of non-dominated plans, instead of one winner, let the same search answer two different questions.
